= Fusion A2A Server
:minisite-index: 100
:minisite-index-title: Overview
:minisite-index-description: What it is and why it exists.
:minisite-index-icon: play
:minisite-nav-next-label: A2A
:minisite-nav-next-link: a2a/index.html

[abstract]
Fusion A2A Server turns a https://yupiik.github.io/fusion/[Yupiik Fusion] application into an
https://a2a-protocol.org[Agent2Agent] agent - discoverable, callable and streamable by any other agent - by reusing the
Fusion JSON-RPC stack: a skill is a plain `@JsonRpc` method.

It implements the https://a2a-protocol.org/v{a2aSpecVersion}/specification/[A2A specification v{a2aVersion}] and serves
both of its JSON bindings, JSON-RPC and HTTP+JSON, on top of one service layer.

== In one snippet

[source,java]
----
@ApplicationScoped
public class MySkills {
    @A2ASkill <1>
    @JsonRpc(value = "report/build", documentation = "Builds a report about a city.") <2>
    public Artifact build(@JsonRpcParam(required = true, documentation = "The city.") final String city) { <3>
        return Artifact.text("report", "all good in " + city);
    }
}
----
<1> Flags the JSON-RPC method as an A2A skill - the flag is stored in the bean metadata at build time.
<2> The method name is the skill identifier and the documentation is what other agents read to decide to delegate to you.
<3> The return type decides the outcome of the task: here it completes with one text artifact.

That is the whole integration: start the application and the agent publishes its card on
`/.well-known/agent-card.json`, answers `SendMessage`, streams its progress and can be polled - see
xref:a2a/skills.adoc[Skills].

== Why it is designed this way

The A2A JSON-RPC binding *is* JSON-RPC 2.0, and Fusion already generates a complete, reflectionless JSON-RPC stack at
build time. So nothing is reinvented:

[options="header",cols="1,3"]
|===
| Concern | Where it comes from
| A2A operations (`SendMessage`, `GetTask`, ...) | plain `@JsonRpc` methods, registered like the ones of the application
| Parameter binding, validation, batching | the Fusion JSON-RPC stack, no reflection at runtime
| Skill discovery | the OpenRPC document the Fusion annotation processor generates plus the `a2a.type` bean metadata
| Skill invocation | `JsonRpcHandler`, i.e. the very same code path as a direct JSON-RPC call
| Operation logic | one binding agnostic service, so the two bindings cannot diverge
| Transport (headers, streams, card) | this project, see xref:deployment/bindings.adoc[Bindings]
|===

Consequences you get for free: no reflection, GraalVM native friendly, a card which cannot drift from the code, and the
ability to expose the exact same methods as a plain JSON-RPC API.

Two properties are load bearing in the implementation itself:

* **nothing blocks**: the protocol, the streams and the webhook calls are asynchronous end to end, and the one place
where an application usually has to block - its own agent logic - is handed off to a virtual thread on purpose, see
xref:internals/design.adoc[Design],
* **one service, two bindings**: `A2AService` holds the shared operation rules and both bindings are thin
adapters on it, which is how section 5.1 - functional equivalence - is satisfied by construction.

== Versioned specification review

The reference is https://github.com/a2aproject/A2A/blob/3303592588e388e62e0f69f701af531d2f4e3991/specification/a2a.proto[A2A `v1.0.1`, commit `3303592588e388e62e0f69f701af531d2f4e3991`], serving the `1.0` wire version.
The proto is authoritative for fields and JSON names; the versioned specification supplies transport and behavioral requirements.
This is an implementation coverage matrix, not a certification that every normative clause has a corresponding test.

[options="header",cols="2,3,3"]
|===
|Area |Implemented scope |Evidence and limits
|JSON-RPC and HTTP+JSON |Shared service logic, routing, tenant/version negotiation, structured protocol errors. |`A2AJSONRPCProtocolTest`, `A2ARestProtocolTest`, `A2AEndpointTransportTest`, `A2ARestRoutingTest` and `A2AErrorsTest`.
|Message/task lifecycle |Send/get/list/cancel, interrupted/terminal states, history limits and task updates. |`A2AServiceTest`, `A2ATasksTest` and protocol tests; blocking timeout now returns a request error, not successful nonterminal work.
|Streaming and notifications |Streaming sends, task subscriptions and ordered webhook notifications. |`A2AStreamingTest`, `SseBusTest`, `PushNotificationTest` and `PushNotifierTest`; webhook endpoint trust and production delivery policy remain deployment responsibilities.
|Agent discovery and security metadata |Public/extended cards, negotiated extensions, signatures and client verification. |`AgentCardTest`, `ExtendedAgentCardTest`, `CardSignerTest`, `CardVerifierTest` and signature tests; declaring a security scheme does not implement authentication enforcement.
|Independent client and protocol |No agent runtime dependency; shared models/codecs and reactive client. |`A2AClientTest`, `StreamSubscriberTest`, model/signature tests and JRE/Tomcat cohosting examples.
|Optional bindings and application extensions |JSON bindings only; extension declarations and required-extension checks. |No gRPC transport or `0.3` compatibility claim; application-specific extension semantics are outside the generic library.
|Full schema and external conformance |Version-pinned source review and focused regression tests. |No exhaustive machine-checked proto-to-record equivalence, official external certification or completed independent expert review is claimed.
|===

The review identified and corrected a blocking-call contract violation: a `SendMessage` request with `returnImmediately=false` must not succeed with a still-working task after its local deadline.
The timeout now fails the request while preserving the task for observation and later completion.
An explicit `returnImmediately=true` still returns the first action without waiting for terminal completion.
Applications still supply authentication/authorization, persistence/retention policy and extension behavior; metadata and integration seams are not substitutes for those responsibilities.
The `Part` convenience record cannot distinguish an explicitly present JSON `data:null` oneof branch from an absent branch, so exhaustive proto-value presence compatibility remains a known model limit.
The subsequent xref:../testing/protocol-conformance.adoc[full-surface support and conformance review] records additional open findings for caller-level authorization, nonblocking sends, cursor pagination and required-field validation.
The implemented-feature rows above must be read with those qualifications; no independent certification is claimed.
