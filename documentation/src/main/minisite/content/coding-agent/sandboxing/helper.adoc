The Linux sandbox helper lives in `coding-agent/extensions/sandbox-helper`.
It is a standalone, JDK-only Java component with a small executable fatjar and a separate native-image build.
It does not depend on the agent framework, a compiled C helper, or a `cc` step to package the JVM artifact.
The native-image variant uses the native-image toolchain and its platform prerequisites; it is not a C helper compiled during ordinary JVM packaging.

The helper supports Linux x86-64 and AArch64 syscall tables.
Availability still depends on the host kernel, namespace policy, executable permissions and the installed distribution; a successful build does not remove these prerequisites.

== Role and process boundary

The helper uses the JDK Foreign Function and Memory (FFM) API to call libc for Linux `prctl`, seccomp installation and `execve`.
These operations run only in a disposable child process, never in the controller JVM.
The helper starts a separate Java proxy bridge before installing the command's filter, waits for bridge readiness, then installs the restrictions and replaces itself with the requested command using `execve`.
It does not fork a running Java runtime to execute Java in a post-fork child.

The trusted bridge forwards the command's loopback proxy traffic to the controller's private Unix socket.
It must start before filtering because the command's filter blocks creation of Unix sockets.
The controller proxy still enforces destination and DNS rules; the bridge is not an unrestricted network grant.
See xref:overview.adoc#_linux_native_commands_and_network_boundary[the Linux network boundary] for the full policy and its limitations.

Bubblewrap (`/usr/bin/bwrap`) remains a Linux system dependency for namespace and mount isolation.
The helper is not a replacement for Bubblewrap, filesystem policy checks or tool-level permissions.
The implementation targets Linux x86-64 and AArch64; this is not a statement that both architectures or their native-image artifacts have been qualified.
The separate macOS launcher is experimental and opt-in; it does not use this Linux helper.
See xref:overview.adoc#_experimental_macos[experimental macOS] for its narrower, offline contract.

Filesystem enforcement uses Bubblewrap mount snapshots, not FUSE.
Before each command, glob rules are expanded against the current filesystem without following symlinks; existing deny matches are masked or mounted read-only.
Missing literal denies do not mask an existing ancestor.

WARNING: Deny rules are not dynamically enforced against future matches during a running command, including currently absent literal targets; they are reconsidered at the next command snapshot.

For concrete `.env.generated` and `AGENTS.md` examples, see xref:overview.adoc#_filesystem_rules_anchors_and_linux_snapshots[filesystem snapshot semantics].
Existing literal allow directories generally permit future children; glob allows grant only existing matching roots, not broad static prefixes.
Unsupported canonical/symlink roots fail closed rather than being silently widened.

== Install missing dependencies on Ubuntu or Debian

Install the distribution's Bubblewrap and certificate packages as an administrator:

[source,bash]
----
sudo apt-get update
sudo apt-get install --yes bubblewrap ca-certificates
/usr/bin/bwrap --version
----

No FUSE package, FUSE mount, C compiler or Docker daemon is required for ordinary sandboxed commands.
Install the build tools your project actually uses separately, for example `sudo apt-get install --yes maven` for Maven.
The JVM distribution also requires JDK 25 or newer on the controller and for the embedded helper; check `java -version` and `JAVA_HOME`.
Distribution JDK package versions vary, so install a supported JDK 25 distribution if your Ubuntu/Debian release does not provide one rather than substituting an older Java runtime.
The native distribution does not need a JDK just to run the helper, but Java projects still need their own JDK.

For a native distribution, install the matching YCA and `sandbox-helper` binaries together in an operator-controlled directory:

[source,bash]
----
# Run from a trusted, unpacked native distribution containing both files.
sudo install -d -m 0755 /opt/yca/bin
sudo install -m 0755 yca /opt/yca/bin/yca
sudo install -m 0755 sandbox-helper /opt/yca/bin/sandbox-helper
/opt/yca/bin/sandbox-helper --probe
----

Do not point `helper.executable` at a group-writable build output or a file the agent can replace.
The native helper must be a regular executable, with neither group-write nor other-write permission; use the packaged sibling or an explicitly reviewed absolute override.
Keep its parent directory protected too.
The JVM distribution embeds its helper classes: do not configure the helper fatjar as `helper.executable`.

=== Namespace or AppArmor failures

Bubblewrap needs usable unprivileged user, mount, PID and network namespaces and kernel seccomp support.
Installing the package alone cannot enable these in a restricted container, CI runner or organization-managed machine.
An `Operation not permitted` or namespace-creation failure can indicate container restrictions, disabled user namespaces or an AppArmor policy; review the host's audit logs and distribution policy with its administrator.
On Ubuntu, keep the distribution's Bubblewrap/AppArmor integration installed and up to date.
Do not disable AppArmor globally, make arbitrary binaries setuid, run YCA with `sudo`, or enable `full_yolo` as an automatic repair.
Choose a host that supports the required isolation or deliberately opt out with `--sandbox false`, understanding that this runs commands on the host without this boundary.
The helper probe below checks seccomp/execve, not namespace support; a native command through YCA exercises both.

== How the agent selects the helper

[cols="1,3",options="header"]
|===
|Deployment |Helper selection
|JVM agent |Core embeds the helper classes and packages them into a tiny `helper.jar` for child execution with Java and native access enabled.
|Trusted override |`yca.sandbox.helper.executable` selects an absolute path to a native helper executable.
|Native YCA distribution |Without an override, the default helper is the `sandbox-helper` sibling of the YCA executable, in `generated/bin/sandbox-helper` in the generated distribution layout.
|===

Set `sandbox.helper.executable` only in trusted global configuration or trusted launch settings, never project-local `.yca/configuration.json`.
The selected file is trusted executable code: use an operator-controlled executable and directory, not a file that agent commands can replace.
The value is an executable path, not a shell command, Java command line or fatjar path.
For example, the nested trusted global JSON form is:

[source,json]
----
{
  "sandbox": {
    "helper": {
      "executable": "/opt/yca/bin/sandbox-helper"
    }
  }
}
----

An empty `helper.executable` keeps the automatic selection described above.
A missing or unusable helper must fail native execution closed rather than silently execute the requested command on the host.
See the xref:../configuration.adoc[configuration reference] for the generated option catalogue.

== Standalone probes

Run these from the repository root after producing the corresponding artifact.
The JVM form requires JDK 25 and explicitly enables native access for the FFM calls:

[source,bash]
----
java --enable-native-access=ALL-UNNAMED \
  -jar coding-agent/extensions/sandbox-helper/target/sandbox-helper-1.0.0-SNAPSHOT-fatjar.jar \
  --probe
----

The standalone native-image counterpart is:

[source,bash]
----
coding-agent/extensions/sandbox-helper/target/sandbox-helper.graal.bin --probe
----

`--probe` installs the mandatory restrictions in its disposable process and attempts to replace that process with `/bin/true`.
A successful exit checks that narrow seccomp/exec path on the current machine.
It does not exercise Bubblewrap, the proxy bridge, filesystem mounts, destination filtering, the agent's default policy or end-to-end native-image distribution behavior.
Do not treat a successful probe as sandbox security qualification.

== Helper invocation contract

The internal command-launch form starts with `SOCKET`, the controller proxy's private Unix socket, accepts repeated `--socket-bridge PORT PATH` arguments for configured generic Unix stream bridges, and ends with `-- COMMAND...` for the command argv.
The launcher also supplies command environment additions through a private file payload, applied only at the final filtered command exec.
Neither these values nor inherited command additions are merged into the trusted helper or bridge startup environment.
It is not a public manual-launch or environment-file recipe; configure `sandbox.environment` and `sandbox.unix.socketBridges` through trusted YCA configuration instead.
The agent supplies this contract inside the Linux sandbox launch; invoking the helper alone does not create the Bubblewrap filesystem or network namespace boundary.
The bridge entry point is internal implementation detail, not a supported public CLI.

Failure to start the bridge, install mandatory restrictions or execute the command is fatal to that launch.
There is no unsandboxed fallback and no automatic policy relaxation.
For policy failures or unsupported roots, review the xref:overview.adoc[sandboxing overview] and xref:overview.adoc#_limitations_and_troubleshooting[current enforcement limitations] rather than bypassing the helper.
