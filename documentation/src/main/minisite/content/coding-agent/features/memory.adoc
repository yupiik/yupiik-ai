yca stores durable preferences and project decisions across sessions.
Facts are written to plain Markdown files and selected into the prompt when a session starts or resumes.

* Save a fact immediately with `memory_write`.
* Inspect stored memory with `/memory`, or request project-memory compaction with `/memory compact`.
* Disable extraction and injection with `memory.enabled=false`.

IMPORTANT: Memory files update live, but the current session's prompt snapshot is frozen.
New or edited facts enter the prompt only in a new session or after resume.

== Overview

[a2s]
....
                     WRITE (live, crash-safe)                    READ (session start only)
  turn ends ──► idle extraction (LLM) ─┐                         session opens / resume
  memory_write (explicit) ─────────────┤                             │
                                       ▼                             ▼
                              MemoryStore.append         BM25-lite ranking
                              (both paths, direct)       (global + project,
                                       │                  recency tie-break)
                                       ▼                             │
                              MEMORY.md files           greedy fill 50/50
                              (global + project,        + spillover <= maxChars,
                               capped maxLines)                 │
                                       │                          ▼
                                       │                 <memory> snapshot in the
                                       │                 stable prefix, cached ONCE
                                       │                 for the session lifetime -
                                       │                 file writes mid-session do
                                       └──►              NOT rewrite it (never re-read)
....

Memory has two scopes:

* *Global*: `~/.yupiik/coding-agent/memory/MEMORY.md`, for user preferences and cross-project rules.
* *Project*: `<project>/.yca/memory/MEMORY.md`, for project decisions and knowledge.

Both use Markdown bullet lists:

[source,markdown]
----
# Memory

Durable facts, decisions and preferences. One bullet per line.

- Always use tabs for indentation.
- The CLI must be backward compatible with v1.
- Run `mvn -q -pl :tui -am package` to build the fat jar.
----

== Writing memory

=== Automatic extraction (default)

When extraction is due after a turn, `MemoryExtractor` asks the model for at most three durable facts.
Each fact has text and a target scope:

[source,json]
----
{
  "facts": [
    {
      "text": "Prefer focused regression tests.",
      "scope": "project"
    }
  ]
}
----

`scope` can be `global` or `project`.
Extraction is:

* *Idle*: asynchronous work while yca waits for input, rather than a blocking part of the turn.
* *Best-effort*: failure does not corrupt memory; warnings identify the failed phase.
* *Throttled*: at least `memory.extractMinChars` new characters (default `1000`) must accumulate before another extraction call.
* *Deduplicated*: a watermark avoids reprocessing excerpts, and `MemoryStore.append` skips exact duplicates.
* *Live*: extracted facts are written directly and durably to `MEMORY.md`, without rebuilding the current prompt snapshot.

Choose extraction cadence with `memory.mode`:

[options="header"]
|===
|Mode |Cadence
|`FULL` |Every `memory.extractEveryTurns` turns (default `3`), plus a todo-completion flush; useful with a distinct cheap model.
|`LAZY` |When all todos are done or at session close; useful when extraction shares the expensive session model.
|`AUTO` (default) |Use `LAZY` when the resolved memory model matches the current model, otherwise `FULL`.
|===

See xref:sessions.adoc#_extraction_input_and_lifecycle[Extraction input and lifecycle] for input filtering, watermarks and nonblocking close behavior.
A cadence checkpoint does not guarantee a remote extraction finishes before process exit.

=== Manual write

`memory_write` persists a fact immediately:

[source,text]
----
memory_write(fact: "The build uses Java 21.", scope: "project")
----

This example stores a project fact; it does not change the running Java version or current prompt snapshot.

=== Near-duplicate replacement

`append` replaces an existing bullet when normalized token Dice similarity is at least `0.8` with at least four shared tokens.
Reformulations therefore replace old wording instead of accumulating.

=== Deterministic cap

Each scope keeps at most `memory.maxLines` bullets (default `200`).
Writes beyond the cap drop the oldest bullets without calling a model.
This remains effective when LLM compaction is disabled or below its size threshold.

=== LLM compaction (optional)

When the project file exceeds 64 KB, `MemoryCompactor` can merge near-duplicates and drop superseded or one-off facts using a compact model.
It runs automatically at most once per session; `/memory compact` requests it manually.
It keeps `MEMORY.md.bak` and discards rewrites that reduce size by less than `20%`.
`memory.compactEnabled` defaults to `true`.
Unlike the deterministic cap, this quality pass costs a model call.

[[choosing-the-memory-model]]
=== Choosing the memory model

The memory path uses `yca.model.memory`, an object containing `name` and optional sampling/output tuning.
It has the same shape as `model.compact` and the accepted legacy `model.prune` setting.
A blank memory `name` falls back to the compact model, then the session provider/model.
Use `$<provider>/<model>` to pin another provider.

A per-provider `backgroundModelOverrides.memory` takes precedence over global memory tuning.
It lets each foreground provider select a local or inexpensive background model without changing the main conversation.

=== Running memory on a local model (llama.cpp)

Memory extraction can be offloaded to a local model.
The following recorded setup served a 1.7 B model on a laptop GPU:

[cols="1,3",options="header"]
|===
|Component |Recorded setup
|GPU |NVIDIA GeForce GTX 1650 Ti Mobile (Max-Q Design), 4096 MiB VRAM, 35 W TDP.
|llama.cpp |`0.4.1-dev`, build 11011, commit aa39d7a3e, Clang 19.1.7, Linux x86_64.
|Model |`unsloth/Qwen3-1.7B-GGUF:Q4_K_M`, 28 layers, 2048 hidden, native context 40960.
|===

Serve it on port 8080 with all layers on the GPU, one parallel slot, a 32 K context, quantized KV cache and flash attention:

[source,sh]
----
llama serve -hf unsloth/Qwen3-1.7B-GGUF:Q4_K_M \
  -ngl 28 --ctx-size 32768 --parallel 1 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --batch-size 128 --ubatch-size 64 --flash-attn on \
  --host 127.0.0.1 --port 8080
----

`-ngl 28` keeps every layer on the GPU; the Q4 weights are about 1.1 GB.
One parallel slot and a quantized KV cache reduce memory demand, while flash attention improves throughput.
This setup fit 32 K context in 4 GiB at roughly 70 tokens/s; results vary by build and hardware.

Declare the local backend, then route only memory to it:

[source,json]
----
{
  "provider": {
    "providers": [
      {
        "id": "remote",
        "baseUrl": "https://api.openai.com/v1",
        "model": "gpt-5-mini"
      },
      {
        "id": "local",
        "baseUrl": "http://127.0.0.1:8080/v1",
        "api": "completions",
        "model": "$local/unsloth/Qwen3-1.7B-GGUF:Q4_K_M",
        "contextWindow": 32768
      }
    ]
  },
  "model": {
    "memory": {
      "name": "$local/unsloth/Qwen3-1.7B-GGUF:Q4_K_M",
      "temperature": 0.6,
      "top_p": 0.95,
      "top_k": 20,
      "max_tokens": 800
    }
  }
}
----

Set `contextWindow` to the served `--ctx-size`, not the model's larger native capacity.
The example uses Qwen3 sampling values `temperature=0.6`, `top_p=0.95`, and `top_k=20`; `max_tokens` bounds one extraction.
If the backend rejects structured facts, extraction falls back to a plain compression snippet.
The fallback improves compatibility but can also fail; it is not a guarantee of a saved fact.

== Selecting memory into context

At session start, yca builds a `<memory>` section in the system prompt, capped by `memory.maxChars` (default `2000`).
It is built once, not reranked or reread on every turn:

[source,text]
----
<memory>
<global>
- Always use tabs for indentation.
- Run `mvn -q -pl :tui -am package` to build the fat jar.
</global>
<project>
- The CLI must be backward compatible with v1.
</project>
</memory>
----

=== Ranking

BM25-lite ranks both scopes against the latest user turn plus the current todo list.
This helps a terse opening prompt retain facts relevant to the active plan.
Selection fills the budget in three steps:

. Global entries receive up to `50%`.
. Project entries receive up to `50%`.
. Remaining capacity spills to relevant leftovers, global first.

=== Why plain markdown + BM25-lite (not a vector store)

Memory is a small set of durable directives, not a transcript archive.
Lexical ranking keeps retrieval model-free and avoids another dependency.

[cols="1,3,3",options="header"]
|===
|Aspect |Current memory |Vector-store alternative
|Retrieval |BM25-lite against prompt/todos, with `p`, `@path` and topic metadata. |ANN similarity over embedded bullets, such as Lucene `KnnFloatVectorField`.
|Models |None for reading; extraction uses an LLM, or manual `memory_write` uses none. |Embedding model for reading and writing, such as ONNX `all-MiniLM-L6-v2` (about 90 MB).
|Storage |Two human-editable, diffable Markdown files. |Index segments and vectors; schema changes can need reindexing.
|Dependencies |JDK only, negligible extra memory. |For example, `lucene-core`, ONNX runtime and a loaded model.
|Latency |Cached token hashes, sub-millisecond ranking and atomic writes. |Initial model loading, millisecond-level ANN queries and per-write inference.
|Matching |Exact keywords and `@path` directives. |Broader semantic topics, with a risk of missing exact-code directives.
|===

Reading memory never costs an LLM call.
Extraction can use a cheap model selected as described in <<choosing-the-memory-model>>.

=== Recency tie-break

New global facts normally sit at the file's tail.
The ranker applies at most a `+10%` recency multiplier as a tie-break, favoring recent facts without letting recency override relevance.

=== No-query fallback

Without a ranking signal, selection takes the head of each scope, bounded to half the budget each.
This covers cases such as a context dump, resume or bare prompt.

=== Durable-directive floor

Even if no global bullet matches, the established global head still receives up to two-thirds of the global half-budget.
Relevance trims stale tail entries rather than dropping all core directives.

=== Frozen prompt snapshot, live files

`memory_write`, extraction and manual edits can update files during a session.
None rebuilds the current `<memory>` snapshot.
A new session or resume selects from the updated files.

This stabilizes the prefix for xref:prefix-cache.adoc[provider caching], but cannot guarantee a cache hit.
If a fact matters now, include it in the current conversation instead of relying on memory to reinject it.

The relative budget uses the resolved provider/model-aware system-prompt cap.

== Tips

* Keep facts and the todo list clear before the next snapshot is built; ranking is not continuous.
* `memory.maxLines` bounds size without a model call; `compactEnabled` improves quality with a model call.
* Edit the Markdown files by hand when needed, then start or resume a session to load the changes.
* Set `memory.enabled=false` to skip extraction and injection entirely; no automatic memory write runs.
